# コードベース改善計画

## 1. 技術的負債の解消

- **`any`型の撲滅**: `src/web/test/setup.ts` で `(globalThis as any)` が使用されています。これはテストコード内での一時的な回避策ですが、より厳密な型定義を検討し、`any`の使用を避けるべきです。
- **マジックストリングの排除**: `WebviewMessage` や `ExtensionMessage` の `command` プロパティは、現在文字列リテラルで管理されています。これを `enum` や `const` オブジェクトに置き換えることで、タイプミスを防ぎ、コードの保守性を向上させます。
  - 対象: `WebviewPanelManager.ts`, `useVscode.ts`, `types.ts`

## 2. リファクタリングと責務分割

- **`StoryDataContext.tsx`の肥大化**: このファイルは現在、状態管理、データ操作ロジック（`findItemAndParent`, `handleDragEnd`）、フォームの表示ロジックなど、多くの責務を抱えています。
  - **提案**:
    - データ操作ロジック（検索、D&D処理など）をカスタムフック（例: `useStoryDataMutations`）として切り出す。
    - フォームの状態とロジックを、専用のコンテキストまたはカスタムフック（例: `useItemForm`）に分離する。
    - これにより、`StoryDataContext`は純粋なデータ供給の責務に集中でき、見通しが良くなります。
- **`StoryYamlService.ts`の責務**: このサービスはYAMLのパースとシリアライズに加え、IDの付与やアイテムの探索・操作ロジックも担っています。
  - **提案**:
    - ID生成ロジックを別のユーティリティクラス/関数に分離する。
    - アイテムの探索（`find...`系）や操作（`add...`, `remove...`系）ロジックを、`StoryFile`モデルを扱うクラス（例: `StoryModel`）としてカプセル化し、`StoryYamlService`は純粋にYAMLとの変換に責務を限定する。

## 3. パフォーマンスの最適化

- **`StoryDataContext`の再レンダリング**: 現在、`storyData`オブジェクト全体がコンテキストの値として提供されています。これにより、データの一部（例: 一つのタスクのステータス）が変更されただけで、コンテキストを利用する全てのコンポーネントが再レンダリングされる可能性があります。
  - **提案**:
    - `React.memo` をコンポーネントに適用し、不要な再レンダリングを抑制する。
    - より高度な状態管理ライブラリ（[Zustand](https://github.com/pmndrs/zustand) や [Jotai](https://github.com/pmndrs/jotai)）の導入を検討する。これらは、コンポーネントが必要とする状態だけを購読できるため、パフォーマンスが大幅に向上します。
    - もしくは、コンテキストを分割する（例: `SelectedStoryContext`, `StoryListContext`）ことで、更新の粒度を細かくする。
- **`ResizableBox`のパフォーマンス**: `onResize`のたびに`AppContent`コンポーネントのステートが更新され、再レンダリングが発生します。
  - **提案**: `onResizeStop` イベントを使用することで、リサイズが完了したときにのみステートを更新し、リサイズ中の不要な再レンダリングを削減できます。

## 4. エラーハンドリングの強化

- **YAMLパースエラーの表示**: 現在、YAMLのパースエラーは`vscode.window.showErrorMessage`で表示され、Webview側にもメッセージが送られます。これは良いスタートですが、よりユーザーフレンドリーにできます。
  - **提案**: Webview側でエラーが発生した場合、どの行で問題が起きているかなど、より詳細な情報を表示する。`js-yaml`の`load`メソッドは、オプションでエラー発生時のコールバックを指定できるため、行番号などの情報を取得可能です。
- **非同期処理のエラー**: `WebviewPanelManager.ts`内の非同期処理（`addItemToStoryFile`など）の`catch`ブロックは、汎用的なエラーメッセージを表示しています。
  - **提案**: エラーの種類に応じて、より具体的で分かりやすいフィードバックをユーザーに提供する。例えば、ファイル書き込み失敗、データ不整合などのエラーを区別する。

## 5. テストの拡充

- **コンポーネントのテストカバレッジ**: 現在、テストが存在しないコンポーネントがあります。
  - **提案**: 以下のコンポーネントに対する単体テスト・結合テストを追加する。
    - `ItemForm.tsx`
    - `Sidebar.tsx`
    - `StoryTable.tsx`
    - `MainLayout.tsx`
- **`StoryYamlService`の境界値テスト**: 正常系のテストは存在しますが、異常系や境界値のテストが不足しています。
  - **提案**:
    - 不正な形式のYAML（例: `epics`がリストではない）を読み込んだ場合のテスト。
    - 空のYAMLファイルを処理するテスト。
    - IDが存在しないアイテムを更新・削除しようとした場合のテスト。

## 6. ドキュメントの整備

- **JSDocコメントの追加**: 主要な関数やクラス、複雑なロジックを持つ部分に説明が不足しています。
  - **提案**:
    - `StoryYamlService.ts`の各publicメソッドに、機能、引数、返り値を説明するJSDocコメントを追加する。
    - `StoryDataContext.tsx`の各関数（`handleFormSubmit`, `handleDragEnd`など）の役割を説明するコメントを追加する。
    - `types.ts` の各型定義に、それが何を表すかの説明を追加する。
- **READMEの拡充**: プロジェクトのセットアップや開発フローに関する説明が不足しています。
  - **提案**: `README.md`に「開発者ガイド」セクションを追加し、ビルド方法、テストの実行方法、デバッグ方法などを記述する。

## 7. ベストプラクティスの適用

- **CSS in JSの検討**: 現在、グローバルなCSSファイル (`App.css`) とコンポーネントが疎結合になっています。
  - **提案**: コンポーネントのスタイルをカプセル化するため、[Styled Components](https://styled-components.com/)や[Emotion](https://emotion.sh/)などのCSS-in-JSライブラリの導入を検討する。これにより、コンポーネント単位でのスタイリングと再利用性が向上します。
- **絶対パスインポート**: プロジェクト内で相対パス（`../`）によるインポートが多用されています。
  - **提案**: `tsconfig.json`の`paths`エイリアスを設定し、`@/components/`のような絶対パスでのインポートを可能にする。これにより、ファイルの移動に強くなり、可読性が向上します。
- **`useVscode`フックの改善**: このフックはデータ取得と状態更新の両方を担っています。
  - **提案**: データ取得（`postMessage`）と状態管理（`useState`）のロジックを分離し、責務を明確にする。例えば、メッセージの送受信だけを行う`useVscodeMessenger`フックを作成し、状態管理は各コンポーネントや別の状態管理フックで行う。
